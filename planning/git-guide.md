# Git для команды JobMatch

Памятка для Клима, Альберта, Влада, Игоря и Матвея. Все команды выполняются в **Git Bash**. Подставляйте свои имя, почту, название ветки и пути к изменённым файлам.

## 1. Что нужно понимать

| Команда | Что делает |
|---|---|
| `git clone` | Один раз скачивает репозиторий и его историю |
| `git status` | Показывает текущую ветку и изменения |
| `git add` | Выбирает изменения для следующего коммита |
| `git commit` | Сохраняет выбранные изменения локально |
| `git push` | Отправляет локальные коммиты на GitHub |
| `git fetch` | Получает историю с GitHub, не меняя рабочие файлы |
| `git pull --ff-only` | Получает изменения и обновляет текущую ветку, если её история не разошлась с удалённой |
| Pull Request (PR) | Предлагает объединить вашу ветку с `main` после проверки |

**Правило команды:** одна задача — отдельная ветка и PR. В `main` напрямую изменения не отправляем. После проверки PR объединяет Клим или назначенный проверяющий. Это правило работы команды; техническую защиту `main` нужно настроить отдельно в GitHub.

## 2. Один раз настроить Git

Установите Git for Windows, откройте Git Bash и проверьте:

```bash
git --version
```

Укажите собственные данные, а не данные Клима или другого участника:

```bash
git config --global user.name "Имя Фамилия"
git config --global user.email "ваша-почта-на-GitHub"
git config --global --get user.name
git config --global --get user.email
```

Используйте подтверждённую почту своего GitHub-аккаунта. Если хотите скрыть почту, скопируйте свой адрес `noreply` из GitHub → Settings → Emails. Имя автора коммитов может отличаться от GitHub-логина.

Эти настройки определяют автора коммитов; вход в GitHub выполняется отдельно.

## 3. Скачать репозитории

Примите приглашение в организацию или репозитории, если оно было отправлено. Затем:

```bash
mkdir -p ~/JobMatch/repositories
cd ~/JobMatch/repositories
git clone https://github.com/CODEXSQUAD/jobmatch-backend.git
git clone https://github.com/CODEXSQUAD/jobmatch-frontend.git
git clone https://github.com/CODEXSQUAD/jobmatch-docs.git
```

В общей папке `JobMatch` репозитории расположены в подпапке `repositories/`. Все три репозитория самостоятельные: у каждого свои ветки, коммиты и PR. Если проект уже скачан в другое место, работайте в существующей папке — повторное клонирование не требуется.

При первом обращении, требующем авторизации, Git Credential Manager из Git for Windows предлагает войти через браузер. Используйте свой GitHub-аккаунт. [Официальная инструкция GitHub по авторизации](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git).

Обычный пароль GitHub не используется как пароль для HTTPS-операций Git. Если браузерный вход не появляется, проверьте установку Git Credential Manager; не вставляйте токен в URL репозитория и не отправляйте его в чат.

## 4. Начать новую задачу

Пример для Игоря. Выполняйте его после проверки `git status`: незавершённую работу сначала сохраните по разделу 8.

```bash
cd ~/JobMatch/repositories/jobmatch-frontend
git status
git switch main
git pull --ff-only
git switch -c feature/frontend-skeleton
```

Ветка создаётся от обновлённого `main`. Если ветка вашей задачи уже существует локально, используйте `git switch ИМЯ_ВЕТКИ` без `-c`.

Предлагаемые первые ветки:

| Участник | Репозиторий | Ветка | Задача |
|---|---|---|---|
| Клим | `jobmatch-backend` | `feature/backend-skeleton` | Backend-каркас и `/health` |
| Альберт | `jobmatch-docs` | `docs/use-cases` | Сценарии и права доступа |
| Матвей | `jobmatch-docs` | `docs/mvp` | Зафиксировать решения по MVP |
| Влад | `jobmatch-docs` | `docs/design` | Ссылка на Figma и описание экранов |
| Игорь | `jobmatch-frontend` | `feature/frontend-skeleton` | Frontend-каркас |

После завершения первой задачи создавайте новую ветку от актуального `main`: например, Альберт — `docs/api-contract`, Матвей — `docs/erd`.

## 5. Сделать коммит и отправить работу

После редактирования файлов:

```bash
git status
git diff
```

Выберите только файлы своей задачи. Например, для frontend:

```bash
git add src package.json package-lock.json README.md
git diff --cached
git commit -m "Создать frontend-каркас и навигацию"
git push -u origin feature/frontend-skeleton
```

Названия файлов выше — пример: указывайте существующие файлы, которые действительно меняли. Для документации это может быть `git add requirements/use-cases.md requirements/permissions.md`.

`git diff --cached` показывает именно то, что попадёт в коммит. Не добавляйте `.env`, токены, пароли, `node_modules`, `bin` и `obj`. До первого коммита проверьте `.gitignore`; сам файл `.gitignore` сохраняется в репозитории.

Если случайно выбрали лишний файл, уберите его из будущего коммита, сохранив изменения на диске:

```bash
git restore --staged ПУТЬ_К_ФАЙЛУ
```

Для следующих коммитов в той же ветке после `git add` и `git commit` достаточно:

```bash
git push
```

Сообщение коммита описывает результат: «Добавить фильтр вакансий по городу», «Описать права работодателя». Избегайте сообщений «fix», «123» и «изменения».

## 6. Создать Pull Request

1. Откройте нужный репозиторий на GitHub.
2. Нажмите **Compare & pull request**. Если кнопки нет: **Pull requests → New pull request**.
3. Проверьте: **base — `main`**, **compare — ваша ветка**.
4. Напишите, что изменили и как проверили. Укажите связанную задачу.
5. Назначьте проверяющего и переведите задачу в Review.
6. После замечаний добавьте исправления обычным коммитом и выполните `git push`: PR обновится автоматически.

Если задача и PR находятся в одном репозитории, запись `Closes #НОМЕР` связывает PR с задачей и закрывает её после слияния в основную ветку. Для задачи из другого репозитория укажите полную ссылку и явно договоритесь о её закрытии.

Проверяющий читает изменения, проверяет запуск или результат документации, затем одобряет PR. Если работа ещё не готова, создавайте **Draft PR**. После слияния PR задача переводится в Done.

## 7. Получить изменения команды

Если работаете в `main` и `git status` показывает чистое рабочее дерево:

```bash
git pull --ff-only
```

Если находитесь в своей ветке и хотите получить изменения, которые коллеги уже объединили в `main`, сначала сохраните свою работу коммитом или временно отложите по разделу 8. Затем, оставаясь в своей ветке:

```bash
git fetch origin
git merge origin/main
```

После успешного объединения проверьте результат и отправьте обновлённую рабочую ветку через `git push`, если она уже опубликована.

Обычный `git pull` в рабочей ветке обновляет её из соответствующей удалённой ветки; он сам по себе не добавляет изменения из `main`.

Каждый из трёх репозиториев обновляйте отдельно.

## 8. Если есть незавершённые изменения

Лучший вариант для законченной части задачи — сделать коммит в своей ветке. Если работа ещё не готова, её можно временно отложить:

```bash
git stash push -u -m "Незавершённая работа перед обновлением"
git stash list
```

`-u` включает новые неотслеживаемые файлы; игнорируемые файлы в это сохранение не входят. Затем обновите нужную ветку по разделу 7. Перед возвратом изменений перейдите в исходную рабочую ветку:

```bash
git stash apply 'stash@{0}'
git status
```

Проверьте, что работа восстановлена. Если она вернулась без конфликтов и всё на месте, удалите использованное временное сохранение:

```bash
git stash drop 'stash@{0}'
```

Команды предполагают, что нужное сохранение — первое в `git stash list`. При нескольких сохранениях выберите правильный номер. Не удаляйте stash до проверки восстановления.

## 9. Если появился конфликт

Конфликт означает, что Git не смог автоматически объединить изменения в одном месте.

Для конфликта после `git merge origin/main`:

1. Выполните `git status`: он покажет конфликтующие файлы.
2. Откройте их в редакторе. Выберите итоговый вариант, согласовав спорные места с автором другой правки.
3. Уберите маркеры `<<<<<<<`, `=======`, `>>>>>>>` и проверьте результат.
4. Завершите объединение:

```bash
git add ПУТЬ_К_ИСПРАВЛЕННОМУ_ФАЙЛУ
git commit -m "Объединить изменения main с рабочей веткой"
git push
```

Если хотите отменить незавершённый merge, выполните `git merge --abort`. Он относится к merge, а не к конфликту после `stash apply`.

При конфликте после `stash apply` сохранение остаётся в списке: исправьте файлы, проверьте восстановление и только затем удаляйте stash. Если непонятно, что оставить, сообщите Климу вывод `git status` и текст ошибки.

## 10. Частые ошибки

| Сообщение | Что делать |
|---|---|
| `Repository not found` | Проверить URL, аккаунт авторизации и принятие приглашения |
| `Permission denied` или HTTP 403 | Проверить доступ на запись и аккаунт, под которым выполнен вход |
| `not a git repository` | Перейти через `cd` внутрь конкретного репозитория |
| `destination path ... already exists` | Использовать существующую папку; не клонировать поверх неё |
| `Your local changes ... would be overwritten` | Сохранить свою работу коммитом или stash |
| `non-fast-forward` при push | В своей ветке выполнить `git fetch origin`, затем `git merge origin/ИМЯ_ВАШЕЙ_ВЕТКИ`, разрешить конфликты и повторить push |
| `Not possible to fast-forward` при pull | Локальная и удалённая истории разошлись. Проверить `git status` и `git log --oneline --graph --all -12`, согласовать объединение с Климом |
| `nothing to commit` | Нет выбранных изменений; проверить `git status` и сохранение файлов в редакторе |

Не исправляйте ошибки через `git push --force`, `git reset --hard` или `git clean -fd` без понимания последствий: можно потерять свою или чужую работу.

## Короткая памятка на каждый день

1. Перейти в нужный репозиторий и проверить `git status`.
2. Для новой задачи: обновить чистый `main` и создать отдельную ветку.
3. Сделать изменения, проверить их, выбрать файлы через `git add`.
4. Выполнить `git diff --cached`, затем `git commit` и `git push`.
5. Открыть PR и попросить проверку.
6. Следующую задачу начинать от обновлённого `main`.
