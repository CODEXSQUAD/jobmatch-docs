# JobMatch — ответственность репозиториев

Статус: рабочая организация для ревью команды. Репозитории `jobmatch-frontend`, `jobmatch-backend` и `jobmatch-docs` уже созданы; описанные ниже исходники и окружение появляются по задачам первой недели.

## 1. Общая схема

| Репозиторий | Ответственность | Ответственные за направление |
|---|---|---|
| `jobmatch-frontend` | Интерфейс сайта и взаимодействие браузера с API | Влад — UI/UX и соискатель; Игорь — кабинет работодателя и окружение frontend |
| `jobmatch-backend` | API, бизнес-правила, база данных и совместный запуск приложения | Клим и Альберт — backend; Матвей — схема БД; Игорь и Клим — окружение |
| `jobmatch-docs` | Требования, сценарии, архитектура, согласованный API-контракт, дизайн и план | Матвей — требования и план; Альберт — сценарии и контракты; Влад — дизайн; Клим — архитектура |

Все участники могут вносить изменения через PR. Ответственный за направление проверяет изменения в своей области, а не становится единственным автором всего репозитория.

## 2. jobmatch-frontend

Отвечает за то, что пользователь видит и делает в браузере:

- страницы регистрации и входа;
- каталог, поиск, фильтры и карточку вакансии;
- форму резюме, кабинет соискателя, остаток лимита и список откликов;
- кабинет работодателя, формы компании и вакансии, список кандидатов и действия над откликом;
- маршрутизацию, формы, клиентскую проверку полей;
- запросы к API, отображение загрузки, пустых данных и ошибок;
- адаптивность и общие UI-компоненты;
- mock-ответы по согласованному контракту на время разработки;
- проверки frontend и основных пользовательских сценариев.

Frontend показывает остаток и отправляет запрос на отклик. Решение о возможности отклика и списании принимает backend. Доступ к PostgreSQL из браузера не предусмотрен.

Предлагаемое содержимое:

```text
jobmatch-frontend/
  src/
    app/                    настройка приложения, маршруты, провайдеры
    pages/                  страницы
    features/               действия: вход, отклик, публикация
    entities/               модели и компоненты предметной области
    shared/                 API-клиент, UI, общие функции
  public/
  tests/                    проверки frontend и сквозные сценарии
  deploy/nginx.conf         раздача frontend и перенаправление /api
  .github/workflows/        проверки и сборка frontend
  Dockerfile
  .env.example
  package.json
  package-lock.json         если команда выберет npm
  README.md                 отдельный запуск и ссылка на совместный запуск
```

Влад отвечает за макеты, общие компоненты и путь соискателя. Игорь — за кабинет работодателя, контейнер frontend, Nginx и CI frontend.

Ко второй лабораторной: React-проект запускается, делает запрос к backend, есть первичные экраны и инструкция.

## 3. jobmatch-backend

Отвечает за то, как приложение работает и какие данные хранит:

- HTTP API и DTO запросов и ответов;
- регистрацию, вход, роли и проверку принадлежности ресурсов;
- резюме, компании, вакансии, каталог и отклики;
- статусы и допустимые переходы;
- дневные лимиты, начисления, списания и журнал операций;
- снимок резюме в отклике;
- транзакции, повторные запросы и конкурентные списания;
- PostgreSQL: модели, связи, индексы, ограничения и миграции;
- вымышленные тестовые данные;
- обработку ошибок, журналы и health endpoint;
- проверки бизнес-логики и API;
- совместный запуск frontend, backend и БД через Compose.

Отдельный репозиторий для БД не нужен: изменения схемы и использующего её backend должны попадать в один PR.

Предлагаемое содержимое:

```text
jobmatch-backend/
  src/
    JobMatch.Api/
    JobMatch.Application/
    JobMatch.Domain/
    JobMatch.Infrastructure/
      Persistence/
        Configurations/
        Migrations/
        Seed/
  tests/
  .github/workflows/        проверки и сборка backend
  Dockerfile
  compose.yaml             совместный запуск трёх компонентов
  .env.example
  README.md                 backend отдельно и весь проект вместе
```

Клим отвечает за архитектуру, интеграцию, авторизацию, резюме, отклики и лимиты. Альберт — за компании, вакансии, поиск и обработку статусов. Матвей проектирует схему и участвует в изменениях конфигураций, ограничений и тестовых данных; миграции проверяются вместе с backend-разработчиками. Игорь ведёт Compose и окружение, Клим проверяет совместный запуск.

Ко второй лабораторной: API запускается, `/health` отвечает, подключение к PostgreSQL работает, есть начальная миграция и инструкция совместного запуска.

## 4. jobmatch-docs

Отвечает за согласованные решения команды:

- проблему, цель, границы MVP и отложенные функции;
- бизнес-правила и варианты использования с критериями готовности;
- роли и права пользователей;
- архитектуру, ERD и словарь сущностей;
- проектируемый API-контракт: пути, поля, примеры, ошибки и права;
- ссылку на Figma, пользовательские потоки и описание дизайн-решений;
- roadmap, обязанности участников и критерии лабораторных;
- записи решений созвонов и причины важных технических решений;
- сценарий демонстрации и материалы защиты.

Предлагаемое содержимое:

```text
jobmatch-docs/
  requirements/
    mvp.md
    business-rules.md
    use-cases.md
    permissions.md
  architecture/
    overview.md
    erd.md
    data-dictionary.md
    decisions/
  api/
    openapi.yaml
  design/
    README.md               ссылка на Figma, потоки, решения
  planning/
    roadmap.md
    team.md
    checkpoints.md
  meetings/
  demo/
    scenario.md
  README.md                 навигация и ссылки на кодовые репозитории
```

Матвей ведёт требования, roadmap и записи встреч. Альберт — сценарии, права и OpenAPI. Влад — материалы дизайна. Матвей с Альбертом ведут ERD; Клим проверяет соответствие реализации и описывает архитектуру. Все участники сохраняют результаты своей работы под собственным авторством.

Ко второй лабораторной: требования и сценарии согласованы, есть принципиальная ERD, основные API-контракты, первичный дизайн и график работ.

## 5. Как репозитории связаны

### API

До реализации API команда согласует `jobmatch-docs/api/openapi.yaml`. Frontend строит запросы и mock-ответы по нему, backend реализует этот контракт.

Swagger/OpenAPI работающего backend описывает реализованное поведение. Согласованный контракт и фактический API должны совпадать: если меняется поле, путь или ошибка, обновляются документация и затронутый код. В связанных PR указываются ссылки друг на друга. Ко второй лабораторной часть контрактов ещё может описывать будущие endpoints; это явно отмечается.

### База данных

ERD и словарь в docs объясняют структуру. Фактическая схема воспроизводится миграциями в backend. При изменении схемы обновляются оба представления.

### Дизайн

Макеты находятся в Figma, ссылка и решения — в docs. Компоненты, стили и страницы — в frontend.

### Совместный запуск

Для первого варианта frontend и backend клонируются в соседние папки:

```text
JobMatch/
  jobmatch-frontend/
  jobmatch-backend/
  jobmatch-docs/
```

`jobmatch-backend/compose.yaml` собирает API из текущего репозитория, frontend из `../jobmatch-frontend` и запускает PostgreSQL. Команда совместного запуска выполняется из backend: `docker compose up --build`. Это планируемый интерфейс запуска, а не уже готовая конфигурация.

Контейнер frontend с Nginx раздаёт сайт и направляет `/api` к API. Для разработки frontend может отдельно работать через Vite с proxy к backend. Docs не требуется запускать для работы приложения.

В backend README описываются нужная структура папок, настройки, миграции и тестовые аккаунты. Для лабораторной фиксируются совместимые версии frontend и backend, чтобы запуск не зависел от случайных последних изменений.

## 6. Что находится на уровне организации GitHub

- Одна GitHub Projects-доска объединяет задачи из всех трёх репозиториев. Задача лежит там, где будет основной результат; связанные задачи получают ссылки.
- Существующий `.github` используется как публичная страница CODEXSQUAD: краткая идея, состав команды и ссылки на три репозитория. Подробные требования находятся в `jobmatch-docs`.
- Workflow-файлы каждого проекта располагаются в его собственной папке `.github/workflows/`.
- Изменения проходят через PR; ревью делает другой участник, знакомый с областью изменения.
- Реальные секреты не коммитятся; `.env.example` содержит только перечень настроек и безопасные примеры.

## 7. Решения для созвона

1. Утвердить три репозитория и ответственных за направления.
2. Утвердить расположение Compose в backend и совместную структуру папок.
3. Принять правило согласования API через docs и обновления связанных PR.
4. Назначить первые задачи и критерии готовности ко второй лабораторной.
